# cairn project memory: design

## Context

Long agentic projects lose track of what was built and why. Today cairn writes good per-plan history (`prd.md`, `plan.md`, `decisions.md`, `RECORD.md` under `docs/sdlc/plans/<date>-<slug>/`). That is all it writes, though:

- Past work reaches a new plan only through one line in `procedures/discover.md:21`, which asks an Explore agent to look at "prior work in `docs/sdlc/`". Plan, build, and review never see it.
- Nothing says how the system works *right now*. A reader has to replay every record in order, and later decisions silently override earlier ones. There are 6 plans and about 9,300 words today, and that grows with every plan.
- The "learnings" that `procedures/learn.md` promises were never built.
- Humans have no rollup. `cairn render` writes a plan list to `docs/sdlc/INDEX.md` (`commands/status.ts:120`), and that's all.

Goal: give future agents and humans fast, accurate memory of what exists, the rules it follows, and why. The approach borrows OpenSpec's split between a living description of the system as it is now and the append-only history of changes, and folds each plan into the living docs at close. The user also wants the config folder renamed from `.sdlc` to `.cairn`.

## Decisions made with the user

1. **Source of truth: living area docs, updated at close.** `docs/cairn/system/<area>.md` describes each area as it is now and is edited in place. Plan folders stay as the append-only history of why.
2. **Each area doc declares the code it covers** in frontmatter `paths:` globs. Close matches the plan's changed files against them. It refuses until every matched doc is edited, or a skip is logged with `cairn area skip <area> --note "<why>"`. Changed files that no area covers are flagged, and learn proposes a new area or adds the paths to an existing one.
3. **Repo-wide decision log.** `cairn decide ... --lasting [--replaces <id>]` marks a decision as architectural. Close publishes lasting decisions to `docs/cairn/decisions/` and marks the ones they replace as `replaced by <id>`. An abandoned plan publishes nothing. Learn checks the flags once before close.
4. **Context is pushed to agents in three places:**
   - The session-start hook injects the index (computed live; see below): about a page of areas with one-line summaries, active lasting decisions, and the last 5 plans.
   - `cairn recall <paths...>` returns the area docs, active decisions, and past plans that cover those paths. Discover and plan call it, and every implementer brief includes the recall for its task's scope.
   - Task and branch reviewers get the active decisions for the changed paths and flag contradictions as Required: fix the code, or record a new decision with `--replaces`.
5. **Layout: tool-owned files hidden, docs visible.** Hidden folders are skipped by default searches (ripgrep) and collapsed on GitHub, so the docs people and agents read stay under `docs/`.
   ```
   .cairn/
     config.json          (was .sdlc/config.json)
   docs/cairn/
     OVERVIEW.md          (generated human rollup)
     system/<area>.md     (living area docs)
     decisions/<id>.md    (repo-wide lasting decisions)
     plans/<date>-<slug>/ (was docs/sdlc/plans/)
     product/PRD.md       (was docs/sdlc/product/)
   ```
6. **Bootstrap: a one-time `/cairn:map`, then growth at close.** Map surveys the codebase, proposes areas with path globs for approval, drafts each doc, and backfills lasting decisions from existing plan folders. After that, the uncovered-files check at close grows coverage.
7. **Area doc shape: one doc for both readers, with learnings inside.**
   ```
   ---
   area: Approvals
   summary: How a human approval is proven.
   paths: [plugins/cairn/hooks/mod/approve.ts, plugins/cairn/cli/src/proof.ts]
   updated: 2026-10-27 (plan: fresh-eyes)
   ---
   # Approvals
   ## Rules          short, imperative; what agents must not break
   ## How it works   prose for people; key files and data flow
   ## Gotchas        learnings, dated, kept with the code they're about
   ## History        generated by the CLI: decisions + plans touching this area
   ```
   No separate `learnings/` folder. `learn.md`'s v0.1 note is removed.
8. **Build it as two implementation plans, run in order on one branch (`project-memory`)**, with the standard superpowers workflow, not cairn (user's call, 2026-10-27):
   - **Plan 1 (mechanical):** the folder rename and layout move. `docs/superpowers/plans/2026-10-27-cairn-folder.md`
   - **Plan 2:** everything else. `docs/superpowers/plans/2026-10-27-project-memory.md`

## Calls I made (check these)

- **Decision ids are `<date>-<slug>`, not `NNN`.** Several plans can run at once, so two closing together would claim the same number. `--replaces` takes that id.
- **Area doc History is generated** by the CLI from the decision log and the plan files. The recorder never writes it, so it stays accurate.
- **`OVERVIEW.md` replaces today's `docs/sdlc/INDEX.md` plan list.** It's generated by `cairn render` and holds three things: areas with summaries and links, a decisions table (active and replaced), and a plan timeline. An HTML view is out of scope for now.
- **Area docs are edited at learn on the plan branch, by the recorder.** Implementers keep the existing rule of never touching cairn docs (`hooks.ts:28`). If two plans in flight edit the same area doc, that's an ordinary merge conflict at ship.
- **Legacy paths are read, never written.** New plans and config go to the new paths. `.sdlc/config.json` and `docs/sdlc/plans/` are still read so that in-flight plans (3 worktrees today) and existing installs keep working. `cairn migrate` moves the files with `git mv`.
- **The index is computed, not stored.** The session-start hook and `cairn index` build it live from the area docs, the decision log, and the plan list. `.cairn/INDEX.md` is not written. A stored copy would go stale between closes and conflict whenever two branches regenerate it, and the hook can build it in milliseconds. `.cairn/` holds only `config.json`.
- **No area docs means no area check.** A repo that hasn't run `/cairn:map` has nothing under `docs/cairn/system/`. Close logs a warning that suggests `/cairn:map` and does not refuse, so existing installs keep closing plans.
- **Uncovered files are skipped once per plan.** `cairn area skip --uncovered --note "<why>"` lets close pass when changed files belong to no area and adding them to one isn't worth it.
- **MVP level:** the area check at close still runs, but a skip note is enough. Recall and the index are always on.
- **Fix plans get the same area check.** They have no learn stage (`stages.ts:17` goes repro → execute → review → ship → closed). The area-doc update runs at ship, where the fix record is written. Fix plans can publish lasting decisions too.
- **The area check reads only the plan's commits, before close writes anything.** Close checks the branch diff against base as it stands when close is called. Only after the check passes does close write its generated output: published decisions, replaced-by marks, History sections, and OVERVIEW. The CLI writes these in one step, and learn commits them (as it does today). Close's own History rewrite therefore can never satisfy the check.
- **"Abandoned" just means the plan never closed.** There's no new abandon stage. Recall and the rollups use closed plans only. Decisions from unclosed plans stay in that plan's `decisions.md`.
- **Recall's plan matches are conservative.** They use the existing `scopesOverlap` (`ready.ts`) between the query paths and each closed plan's task scopes, newest first, capped at 5. Old plans without scopes are skipped. Areas and decisions are the main signal; past plans are a pointer.
- **Rules when old and new folders coexist.** If both `.sdlc/` and `.cairn/` exist, `.cairn` wins and status warns. `listPlans`, render, and recall read plans from both `docs/cairn/plans/` and `docs/sdlc/plans/`. A plan already under the old folder keeps writing there until it merges. The cairn-docs exclusions in `hooks.ts`, `phase.ts`, and `tasks.ts` cover both roots.
- **Sizes for INDEX and the decision log.**
  - INDEX is capped at about 60 lines. Recent plans are trimmed first, then the summaries of active decisions. Areas are never trimmed.
  - "Active" means `status: active`. A `--replaces` that points at an unknown id makes decide refuse.
  - `--lasting` requires `--areas` or `--paths`, so every lasting decision can be found by recall and review.
- **Both plans run on one branch, Plan 1 first.** No plan is in flight today: all six are closed, and the three leftover worktrees belong to closed plans. So Plan 1 can run `cairn migrate` on this repo safely, and it can also prune those worktrees.

## Plan 1: the folder move

Replace the hard-coded paths with constants and add legacy fallbacks:

- `cli/src/config.ts:5` `CONFIG_REL`: `.cairn/config.json`, with a fallback read of `.sdlc/config.json`.
- `cli/src/locate.ts:7` `PLANS_DIR`: `docs/cairn/plans`. Plan lookup also resolves `docs/sdlc/plans/` (the same way it already handles undated legacy folders).
- `docs/sdlc/` literals become shared constants: `commands/tasks.ts:137-146` (the stray and dirty checks), `commands/phase.ts:33,38` (the test reuse diff excludes cairn docs, so exclude both roots), `commands/hooks.ts:28,49`, `commands/plans.ts:60-65` (product), `commands/status.ts:120` (render), `commands/fix.ts:29`.
- New `cairn migrate`: `git mv .sdlc .cairn` and `git mv docs/sdlc docs/cairn` when no plan is in flight. Otherwise it refuses and names the in-flight plans.
- Docs: every procedure, agent, skill, template, `references/cli.md`, `hooks/NOTES.md`, README, and CLAUDE.md that names the old paths. Mod files that read plan paths (`hooks/test/world.tsx` and the files grep finds) change too.
- Doc tests that assert path strings (`*-doc.test.ts`, `procedures.test.ts`, `records.test.ts`, `dated-folders.test.ts`, …) are updated on purpose.
- Run `cairn migrate` on this repo. Bump `plugin.json` version.

## Plan 2: project memory

**Phase 1: area docs, recall, and the close check**
- `cli/src/areas.ts`: load `docs/cairn/system/*.md` frontmatter (area, summary, paths), and match files with the existing `glob.ts` `matchesAny`.
- `cairn recall <paths...> [--json]`: matching areas, the active decisions whose paths or areas match, and past plans whose task scopes (in `state.json`) overlap.
- At close (`commands/stages.ts`): diff the plan branch against base, match the changed files to areas, and refuse unless each matched doc changed on the branch or has an `area skip` log entry. List uncovered files as a refusal with the fix ("add these paths to an area or create one").
- `templates/area.md`. In `learn.md`, add an "Update area docs" step before Findings, run by the recorder from the diff and the plan log.

**Phase 2: lasting decisions**
- `cairn decide --lasting [--replaces <id>] [--paths/--areas]` stores the flag in state and in `decisions.md`.
- At close, write `docs/cairn/decisions/<date>-<slug>.md` (frontmatter: id, status, replaces, areas, paths, plan) and set `status: replaced by <id>` on what it replaces.
- In `discover.md`, `plan.md`, and `fix.md`, tell the interviewer when to use `--lasting`. In `learn.md`, check the flags once.

**Phase 3: delivery**
- `cairn render` writes `docs/cairn/OVERVIEW.md`, and close re-renders it. `cairn index` prints the index. The generated History section is rewritten in each touched area doc.
- `hookSessionStart` (`commands/hooks.ts:19`) adds the index to its output whether or not a plan is active, with a size cap.
- Discover and plan run `cairn recall` on what the request touches. Execute adds the recall for the task scope to each implementer brief. The `task-reviewer` and `branch-reviewer` agents, and `references/review-checklist.md`, gain a "contradicts an active decision" check.

**Phase 4: `/cairn:map` and backfill**
- `skills/map/SKILL.md` and `procedures/map.md`: survey (Explore agents), propose areas with globs through AskUserQuestion, draft the docs, and backfill lasting decisions from existing `decisions.md` files. It runs on main, outside any plan, like the product track (`procedures/product.md`).
- Run it on this repo.

## Non-goals
- Semantic or vector search. Recall is path- and area-based and deterministic.
- HTML or web rendering of the overview.
- Rewriting past plan records.
- Configurable folder names.
