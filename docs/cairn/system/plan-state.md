## Rules

- Only the CLI writes `state.json`. Every write goes through `mutate`, which holds the plan lock for the read-change-save (`plugins/cairn/cli/src/shared.ts:95`, `util.ts:46`).
- Every stage move needs its proof. A missing proof throws `Refusal` with the exact fix (`commands/stages.ts:193-221`).
- Skipping a check goes through `gate` and needs the user's proof. The override and its reason are logged (`shared.ts:73`).
- A paused plan cannot advance or finish a phase (`stages.ts:195`, `commands/phase.ts:28`).
- Approving ship needs a passing review. Close needs the record check, the tests, and the area-doc check (`stages.ts:164`, `closeGates`).
- Changing stage clears the recorded step, so a step never outlives its stage (`shared.ts:98-100`).
- Renaming a stage or step means updating `STEPS` and `STEP_LABEL` (`types.ts:16-21`) and the procedures that `cairn next` names.
- Close comes before merge. The merge is offered last, so every record lands on main.
- `plugins/cairn/references/cli.md` is the CLI contract. Update it whenever a command or a JSON shape changes.

## How it works

A plan's state lives in one `state.json` in its plan folder. `state.ts` loads and saves it. Each save also rewrites `STATUS.md` from it. `types.ts` defines the stages in order: repro, discover, prd, plan, execute, verify, review, ship, learn, closed.

`main.ts` parses the command line and hands it to a handler re-exported from `commands.ts`. The handlers in `commands/` (stages, phase, step, status, pause) each look up the plan, then change state inside `mutate`. `cmdApprove` records a human approval for the PRD, the plan, or ship. `cmdAdvance` moves to the next stage. It runs the checks for the stage being left and refuses with the fix if one fails.

The reading side is `cairn next` and `cairn status`. `render.ts` turns state into the next-action text and the status JSON, and `cmdNext` maps the stage and step to a procedure file. Late-stage steps are recorded with `cairn step` from a fixed list, and every surface renders the wording from status.

## Gotchas

- 2026-10-21: Close-only-when-merged deadlocked a plan, and squash merges never counted as merged. Close now comes first and the merge last. Status shows "Closed · PR open" until the merge lands.
- 2026-10-21: The recorded test summary is the last count line of the test output, which can be `fail 0` instead of the pass count. Still open.
